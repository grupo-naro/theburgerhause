# Demora Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show customers an estimated wait (automatic from kitchen load + manual "demora" with minutes and a staff-only reason) in the menu and in "Tu pedido".

**Architecture:** A pure estimate function (`src/lib/delay/estimate.ts`) fed by SQL reads over `order_events` and the count of `en_preparacion` orders; a `delay_notices` table holds the manual delay (one active row, immutable history); a new `DELAY_CHANNEL` Postgres NOTIFY (copy of `STOCK_CHANNEL` wiring) refreshes staff screens; the public side reads through a public route `/api/demora` polled by one client component used by the menu layout and the tracking view. The reason never leaves the server except to staff pages.

**Tech Stack:** Next.js 16 (read `node_modules/next/dist/docs/` first: breaking changes), React 19, Drizzle + PostgreSQL, zod via `@/lib/zod`, Vitest unit + `*.int.test.ts`, Playwright (`desktop` + `mobile`).

**Spec:** `docs/superpowers/specs/2026-10-26-demora-design.md` (read it and its "Aclaraciones").

## Global Constraints

- UI text in Spanish (es-AR); mobile first, touch targets ≥ 44 px in the staff panel.
- Next migration is `0012_*` after `0011_orders_tanda.sql`; follow how 0011 was generated (`pnpm db:generate`, journal in `src/db/migrations/meta`).
- Every new Server Action / Route Handler / page is classified in `src/lib/security/surface.ts`; regenerate `docs/ops/security-surface.md` with `UPDATE_SURFACE_DOC=1 pnpm test:security`.
- No hard deletes: manual delays are closed (`ended_at`), never removed.
- One live connection per page (`LiveRefresh` in `StaffShell`): do not mount another.
- The reason (`reason`) must never appear in any public DTO, public route response, public page props or `/pantalla`.
- Manual extra minutes: multiples of 5, 5–60. Reason: required, trimmed, 1–120 chars. Defaults: `basePrepMinutes` 25, `deliveryTravelMinutes` 15.
- No screenshots in verification (the owner checks by eye). Gates before each commit: `pnpm lint`, `pnpm test`; integration tests via `pnpm test:int` (never concurrent with e2e; Docker Desktop running); `pnpm test:security` when `surface.ts` changes; `pnpm build` at the end of Tasks 4 and 5.

## Review Focus

- Zero completed orders today (first deploy, empty night): estimate = base time, no NaN/0, no crash.
- 50+ orders `en_preparacion` at once: estimate high but capped (≤ 90 min kitchen), never absurd.
- Tanda edits (same-status events) must not count as preparation durations.
- Activating a delay while another is active replaces it (two history rows, one active); double-tap must not create two actives (partial unique index).
- Deactivating when none is active: harmless "ya no hay demora" result, not an error page.
- Customer pages still render when the DB read for the estimate fails (banner hidden, page up).
- Cached menu must not freeze the banner: the banner is a dynamic hole plus client polling, never part of `getMenu()`.

### Task 2: Estimate engine

**Files:**
- Create: `src/lib/delay/constants.ts`, `src/lib/delay/estimate.ts`, `src/lib/delay/estimate.test.ts`, `src/lib/delay/queries.ts`, `src/lib/delay/queries.int.test.ts`
- Test helper: reuse `src/db/test-utils.ts`

**Interfaces:**
- Produces in `constants.ts`: `SAMPLE_WINDOW = 20` (orders), `SAMPLE_MAX_AGE_MIN = 180`, `MIN_SAMPLES = 5`, `FREE_QUEUE = 6`, `MIN_PER_EXTRA_ORDER = 1.5`, `MAX_QUEUE_SURCHARGE = 60`, `MAX_KITCHEN_MINUTES = 90`, `RANGE_HALF_WIDTH = 5`, `ROUND_TO = 5`, `DELAYED_THRESHOLD = 10`.
- Produces in `estimate.ts`:
  - `type EstimateInput = { samplesMinutes: number[]; inPreparation: number; baseMinutes: number; travelMinutes: number; manualExtraMinutes: number; fulfillment: Fulfillment }`
  - `type Estimate = { low: number; high: number; delayed: boolean }` (minutes, multiples of 5)
  - `computeEstimate(input: EstimateInput): Estimate`
- Produces in `queries.ts`:
  - `loadPrepSamples(db: Db, now: Date): Promise<number[]>` (minutes per order, newest `SAMPLE_WINDOW` within `SAMPLE_MAX_AGE_MIN`)
  - `countInPreparation(db: Db): Promise<number>`
  - `loadEstimateInputs(db: Db, now: Date): Promise<{ samplesMinutes: number[]; inPreparation: number }>`
- Consumes: `Fulfillment` from `src/domain/order-status`.

Rules for `computeEstimate`: kitchen = median(samples) if `samples.length >= MIN_SAMPLES` else `baseMinutes`; `kitchen += min(MAX_QUEUE_SURCHARGE, ceil(max(0, inPreparation − FREE_QUEUE) × MIN_PER_EXTRA_ORDER))`; `kitchen = min(kitchen, MAX_KITCHEN_MINUTES)`; `center = kitchen + manualExtraMinutes + (fulfillment === "delivery" ? travelMinutes : 0)`; round `center` to `ROUND_TO`; `low = center − RANGE_HALF_WIDTH` (never below 5), `high = center + RANGE_HALF_WIDTH`; `delayed = manualExtraMinutes > 0 || kitchen − baseMinutes > DELAYED_THRESHOLD`.

`loadPrepSamples`: per order, minutes between its latest `order_events` row with `to_status = 'en_preparacion'` and the first later row with `to_status IN ('listo_despacho','para_retirar')`, ignoring rows where `from_status IS NOT DISTINCT FROM to_status` (tanda edits); only orders whose ready event is newer than `now − SAMPLE_MAX_AGE_MIN`; ignore non-positive durations.

- [ ] **Step 3: Implement** `constants.ts` and `computeEstimate` (pure, no imports from `next/*` or the DB).
- [ ] **Step 4: Run** the unit test → PASS.
- [ ] **Step 5: Write failing integration tests in `queries.int.test.ts`**: orders with events in/out of preparation yield the right minutes; a tanda event (`from_status = to_status = 'en_preparacion'`) between does not shift the start; orders older than 180 min are excluded; an order still in preparation has no sample; `countInPreparation` counts only `en_preparacion` (delivery and takeaway) and not `pendiente_aprobacion` or `listo_despacho`.
